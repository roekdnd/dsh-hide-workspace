# DSH：让左侧栏支持「隐藏工作区」— 可行性讨论

> 调研对象：`<DSH_INSTALL>`（DSH 0.2.1-rc.3，Electron）
> 方法：解包 `resources/app.asar`（305 个 `@deepseek-ai/*` 包），逐行核对源码 + README，
> 并运行两个最小复现脚本验证关键机制。全程只读，未改动 App 与你的 `workspace.json`。

---

## 一、结论先说

你的需求（工作区「暂时隐藏、可恢复」，非删除）**在 DSH 里完全合理，而且产品内部已有同构的先例**——
会话（Session）就支持「归档 / 取消归档」：从列表消失、历史与位置保留、可恢复、带撤销。

但有两个硬事实，决定了不能走「加个菜单项的轻量插件」这条路：

1. **DSH 没有为「工作区级别」预留任何扩展点**（我把全部 305 个包扫完了，见第二节）；
2. **数据层过滤会把会话赶到「未分组」里冒出来**，而不是把它们藏起来（见第三节开头）——
   也就是说，"从数据里删掉" 和 "你要的隐藏" 是两件不同的事。

能做到，但要选方案。**我的推荐是「方案 C（CSS 就地隐藏）+ 方案 B（面板作为管理界面）」的组合**，
理由见第七节。

---

## 二、为什么不能简单加一个菜单项

### 现状：工作区那行 `⋯` 菜单是写死的

`dsh-client-ui-workspace/lib/client.js` 约 L1951 的 `ProjectRowItem`：

```js
const workspaceMenuItems = [
  { id: "rename", label: t("rename"),              icon: IconEditOutlineRegular },
  { id: "delete", label: t("delete.workspace"),    icon: IconTrashOutlineRegular, danger: true },
];
...
onSelect: (id) => {
  setMenuOpen(false);
  /* v8 ignore next -- Menu can emit only the rename and delete rows supplied above. */
  if (id !== "rename" && id !== "delete") return;   // ← 其它 id 直接忽略
  if (id === "rename") actions.rename(); else actions.delete();
}
```

**关键点：`ProjectRowItem` 整个函数体内没有任何 `renderSlot(...)` 调用。**
我核对了该包全部 7 处 `renderSlot`：分别在 L2155 / 2307 / 2345 / 2349 / 2713 / 3933 / 4516，
全部是 **会话级**（`sidebar.workspaces.session.menu.item`、`.session.row.action`）、
`directoryFlow` 或 `workspace.toast`。

### 槽位清单（`client.js` ~L5221）证明没有工作区级菜单槽

```js
ctx.slots.inject("sidebar.workspaces", () => ctx.slots.register({
  name: "sidebar.workspaces",
  children: {
    "sidebar.workspaces.directoryFlow":      { kind: "single", scope: "root" },
    "sidebar.workspaces.session.menu.item":  { kind: "list",   scope: "root", ... },
    "sidebar.workspaces.session.row.action": { kind: "list",   scope: "root" },
    "sidebar.session.row.leading":           { kind: "list",   scope: "root" },
    "sidebar.session.row.hover":             { kind: "list",   scope: "root" },
  },
  store: viewStore,
  inject: browserInjected,
  locale: NS
}, WorkspaceBrowser));
```

对照组：**会话**菜单之所以能被插件扩展，是因为它是 `list` 槽，且官方自己就把
`pin(100) / rename(200) / fork(300) / archive(400) / session-id(450)` 注册成了槽条目
——「reusing a shipped id at another priority shadows that action」。工作区没有这一层。

> 一句话：会话是可扩展的，「工作区」这一行是封闭的。这是本次所有取舍的根源。

### 我把 305 个包全扫了一遍，确认这不是「我没找对 API」

我把安装里所有 `slots.inject("…")` 目标全部导出、去重，完整清单里与工作区相关的**只有 7 个**：

```
conversation.hero.workspace                  ← 空态里的工作区选择器
conversation.hero.workspace.directoryFlow    ← single：选目录交互
sidebar.workspaces                           ← single：整个浏览器面板（遮蔽目标）
sidebar.workspaces.directoryFlow             ← single：选目录交互
sidebar.workspaces.session.menu.item         ← list：**会话**菜单行
sidebar.workspaces.session.row.action        ← list：**会话**悬停按钮
workspace.toast                              ← 归档提示的呈现
```

**没有任何一个是「工作区行的菜单」或「工作区行的动作」。** 所有能挂动作的 `sidebar.*` 槽，
要么作用域是 Session，要么是面板（`sidebar.panellist` / `sidebar.right.*`），要么是外壳装饰
（`sidebar.brand.*` / `sidebar.toggle.badge` / `sidebar.footer.action` / `sidebar.settings`）。

所以「加一个菜单项」这种轻量做法在架构上不存在——不是找不找得到 API 的问题。

## 三、可行方案（按侵入性从低到高）

### ⚠️ 一个必须先说清的关键事实：**数据层过滤 ≠ 隐藏行**

我一开始以为「把工作区从数据数组里滤掉」就能达到目的。**这是错的**，R2 帮我纠正了。

`groupByWorkspace()`（L1027）里 `accounted` 这个集合**是从传进来的 `workspaces` 数组累加出来的**：

```js
for (const workspace of workspaces) {
  for (const id of workspace.sessionIds) {
    accounted.add(id);        // ← 只记录「传进来的」工作区里的会话
    ...
  }
}
const stray = list.ids.filter((id) => !accounted.has(id) && ...);  // 剩下的都算「未分组」
if (stray.length > 0) groups.push(buildGroup("", ...));            // → 变成「未分组」组
```

所以把你隐藏的工作区从数组里拿掉，**它下面的会话不会被藏起来，而是全部落进「未分组」里冒出来**。
L3543 还有第二处同样的重算（`ungroupedMemberIds`）。

**你要的效果是「连会话一起消失」，所以必须让那一行不渲染，而不是让它从数据里消失。**
这一点决定了下面方案排序——也让我原来推荐的方案 A 从「推荐」降级。

---

### 方案 A — 接管 `sidebar.workspaces` 整槽（设计上最正确，但有个要命的门槛）

`single` 槽的选举逻辑（renderer L1173）取 `entriesOfSlot(key)[0]`，按 `priority` 升序，
冲突提示原文是 `register at a different priority to shadow it (lowest renders)`。
我用最小复现验证过（`notes/_scratch/slot-shadow-proof.mjs`）：

```
after upstream only        -> renders: ui-workspace-shipped
after our -100 plugin      -> renders: better-sidebar      ← 低优先级成功遮蔽
same-priority register     -> THROWS: ... already has an entry at priority 0
```

**但 R2 找到了一个我没预料到的致命阻断**：SlotCore 拒绝重复声明已存在的子槽。

```js
for (const key of Object.keys(e.children)) {
  const rec = this.records.get(key);
  if (rec?.spec) throw new Error(`slot "${key}" is already declared (by ...)`);
}
```

而官方 `sidebar.workspaces` 这个条目身上挂了 **5 个子槽**（`directoryFlow`、`session.menu.item`、
`session.row.action`、`session.row.leading`、`session.row.hover`）。于是成为死局：

- **不声明这 5 个子槽** → 会话菜单、悬停按钮、leading 座、悬停卡，**以及「添加工作区」的目录选择流全部消失**；
- **声明它们** → 直接抛错。

**结论：方案 A 不是「写个插件」，而是要 vendoring 约 4100 行**（view store、导航服务、CSS、
行组件、AnimatedRows、picker、浏览器+树+弹窗、会话动作、约 200 条文案）。
这已经是 **fork 整个包**，不是插件。所以它排不到第一。

- 成本：极高
- 健壮性：走官方槽位机制，不是 DOM 补丁
- 风险：官方升级改动 props 契约就得跟

### 方案 B — `sidebar.panellist` 新开一个面板（完全可以，但不是你要的那个功能）

侧栏允许插件注册**主面板**（`sidebar.panellist` + `main` keyed 槽），Plugins / 自动化任务就是这样来的，
**没有任何 hack，一整套标准设施白拿**。

- 成本：低-中，最干净
- 但 **不满足你的原始诉求**：它是在侧栏多一个入口，不是在现有列表里少几行。
- 定位：**适合当「隐藏工作区管理器」的配套 UI**，不适合单独当功能。

### 方案 C — CSS / DOM 隐藏（唯一能「就地隐藏」且不用 fork 的做法）

工作区行的 `data-row-key` 是 **`workspace:<workspaceId>`**（`group.key === workspace.workspaceId`，
`buildGroup(workspace.workspaceId, ...)` L1041）。但 R2 指出：**外层组容器没有 id 属性**，
要连会话一起藏（也就是你真的想要的效果），得用 `:has()`：

```css
/* 只藏组头：会把该组的会话留在原地变成孤儿行，不建议 */
[data-row-key="workspace:<uuid>"] { display: none; }

/* 连整组一起藏（推荐） */
div:has(> [data-row-key="workspace:<uuid>"]) { display: none; }
```

**R2 已核实的好处：**
- **没有任何计数会被弄坏**：`sessionCount`（L1106）算出来后**全项目没有任何地方渲染它**
  （305 个包里只有这 1 处出现），`sessions.count.one/other` 也是 0 个调用点。
  ——我之前担心的「计数会错」是不成立的。
- **搜索结果不受影响**：搜索行没有 `data-row-key`，且不在 AnimatedRows 里。
- 折叠态（rail）下天然无操作。

**R2 已核实的两个真实隐患（都能绕过）：**
1. **拖拽落点**：拖拽锚点用的是「已渲染的 groups」（L3137），对着被隐藏的兄弟节点拖会提交
   一个看不见的换序 → 隐藏模式下建议**禁用工作区拖拽**。
2. **动画测量**：AnimatedRows 用 `querySelectorAll('[data-row-key]')` + `getBoundingClientRect()`（L2489），
   被 `display:none` 的元素拿到零尺寸矩形，位移动画会算错 → 用 `visibility` + 0 高度
   或干脆在该模式下关掉行过渡。

- 成本：极低（几十行 CSS + 一个管理面板）
- 风险：`data-row-key` 是动画器的内部属性，不是公开 API（官方规范也禁止读别的插件的 DOM）

### 方案 D — 直接改官方 `lib/client.js` / `app.asar`

R2 顺带查清了两件事：`app.asar` 头部**没有 integrity 块**，且 `DeepSeek Harness.exe`
**没有启用 asar 完整性校验的 fuse** —— 所以打补丁**技术上确实能加载**。
但：没有任何受支持的「按包覆盖」机制（loader patch 会断言行名，client 路径由解析出的包根推导），
且 electron-updater 每次更新会整个替换安装目录，**每次升级都要重打一遍**。
只适合你完全不想维护的场景。

## 四、状态存哪里（这块是好消息）

「隐藏」这个标记**不能**塞进现有的 `workspace.json`。我验证过原因：

`dsh-workspace` 的工作区记录是普通 zod `z.object()`（**strip 模式**，不是 strict）：

```js
export const workspaceRecord = z.object({
  path: z.string(), title: z.string(), sessionIds: z.array(sessionId),
  createdAt: z.string(), updatedAt: z.string(),
});
```

用 App 自带的 zod 实测（`notes/_scratch/zod-strip-proof.mjs`）：多塞的 `hidden: true`
**被静默丢弃，且不报错**。而且该 domain 是独占的（`already-open`），第三方无法再开一个句柄。

**正确做法：插件自己声明一个独立 storage domain**，落到自己的文件：

```
%USERPROFILE%\.dsh\storages\workspaces_hidden.json
```

API 就是官方 `dsh-workspace` 自己用的那套：

```js
const hiddenWorkspacesSpec = defineDomain({
  name: 'workspaces_hidden',            // 必须匹配 /^[a-z][a-z0-9_]*$/
  version: 1,
  layout: 'per-record',
  invalidRecords: 'backup-and-skip',    // 数据坏了也不要弄坏侧栏
  tables: { hidden: domainTable(hiddenState) },
});
const domain = await ctx.storageDomain.open(hiddenWorkspacesSpec);   // inject: ['storageDomain']
```

数据形状（推荐）：键为 workspaceId 的 map，隐藏/取消就是 set/delete，天然幂等：

```jsonc
{ "unit": { "name": "workspaces_hidden", "version": 1 }, "global": null,
  "tables": { "hidden": { "state": {
    "hidden": { "<workspaceId>": { "hiddenAt": "2026-10-25T12:34:56.789Z" } }
  } } } }
```

两个踩坑提醒：
- **千万别动 `version`**：没有自动迁移，bump 版本会让插件在 open 时直接 `version-mismatch` 起不来。
  后续加字段用 `.optional()` / `.default()`，版本号不动（官方 `archivedSessionIds` 就是这么做的）。
- 存在 `localStorage` 里**不可行当主存**：桌面端 origin 虽然是固定的 `dsh-app://app`，但它不跨端同步
  （官方 `dsh-client-shortcuts/README:34`：Web 用 origin-local，Desktop 用 device-local，两者互不相干）。
  而且官方多处写着「legacy localStorage values are ignored」。**只能当缓存。**

## 五、交互设计建议（沿用官方「归档」语义）

产品里**没有** snooze / mute 概念（全仓只有 DevTools 里无关的字符串），所以别造新词。
官方对「隐藏会话」的原话是：

> **Hide** a session from the grouping when it should stop appearing there: it disappears from the
> visible list, while its session, history, and place in the project stay intact.

建议照抄这套，三条设计纪律：

1. **隐藏项保留原位置** —— 纯 sidecar 元数据，绝不碰 `workspaceIds` 顺序和 `tables.workspaces`。
2. **可逆动作给「撤销」toast，不给确认弹窗** —— 官方归档就是这样（只有「有任务在跑」时才弹确认）。
3. **给隐藏项一个看得见的家** —— 扩展现有三段式 `archivedFilter`，加一个
   **显示已隐藏工作区**；空状态给「暂无隐藏工作区」+「查看全部」。

用词建议（与现有中文 UI 一致，`已核对`）：

| 位置 | 建议文案 | 参照的现有文案 |
|---|---|---|
| 菜单项 | 隐藏工作区 | `重命名` / `删除工作区` |
| 恢复 | 取消隐藏 | `取消归档` |
| 筛选 | 显示已隐藏工作区 | `全部对话（显示已归档）` |
| 状态标记 | 已隐藏 | `已归档` |
| 撤销 | 撤销 | `撤销` |

## 六、怎么装（实测结论，有几个反直觉的点）

### 6.1 装一个本地插件只需要两样东西（不是三样）

1. `profiles\desktop\cordis.patch.yml` 里加一条 `insert:` 行 —— 这才是真正「挂载」插件的动作，
   **也是让浏览器半边被加载的原因**（浏览器图是按 live Loader 行扫描出来的，没有行就没有 client half）。
2. 包能被 Node 从 profile 目录解析到，即 `profiles\desktop\node_modules\<name>` 存在
   （用 `link:` 依赖 + pnpm 建立）。

`dsh.profile.bundles` + `dsh.bundle.patch` 是**另一条等价路线**（把行的声明搬进包自己里），
**二选一，不要都做**。你现有的两个例子正好各走一条：`anchored-standard` 两条都用了，
`dsh-our-free-model` 只用了 bundle 路线、profile 里根本没有它的 patch 行。

### 6.2 三个容易踩的坑

- **纯 UI 插件也必须有 `index.js`（host 半边）**，哪怕内容是空的。
  官方 50/79 个带 `dsh.client` 的包就是 `export function apply() {}`。官方注释写得很直白：
  「the empty apply exists **so the plugin appears in the host cordis.yml / Loader**」。
- **`dsh.client.inject` 不是服务注入**，它只是模块到达顺序；真正的服务注入是 `client.js` 里
  `export const inject = [...]`。这个名字很有误导性。
- **绝对不要用 `mklink /J` 建目录联接**：Windows junction 的 `isSymbolicLink()` 返回 `false`，
  而 DSH 的 linked-root / peer 解析恰好用这个判断，会变成「看起来装上了但解析行为诡异」。
  **必须用 `pnpm add link:<绝对路径>`**。

### 6.3 想让插件出现在「插件」面板里，就必须打成真正的 bundle

这点和你的使用习惯直接相关。插件面板**接受本地绝对目录**，但会先查 `dsh.bundle.patch`，
没有就报 `not-a-bundle` 拒绝。官方原文：

> Only bundles are managed — … and **loading plain plugin modules stays a file operation**.

所以：**想要卡片 + 开关 + 卸载按钮 → 打包成 bundle（自带 `cordis.patch.yml`）**，
然后在「添加插件」里填绝对路径，全程不用手改 profile 文件。
只走 patch 行那条路的话，面板里看不到它。

### 6.4 开发热更新（这块体验其实不错）

- **改 `client.js` → 约 0.5 秒自动生效**，窗口不刷新、不重启（`dsh-client-hmr` 每 500ms 轮询 mtime/size）。
  代价是插件内 React state 会丢，但会话/工作区/连接状态都还在。
- **改 `cordis.patch.yml` → 热生效**，不重启（`dsh-hmr` 监听 profile manifest 和两个用户 patch 文件）。
- **新增包 / 新增 `link:` → 需要重启一次**（运行期解析在启动时算好，
  `dsh-app-boot` 明确拒绝在运行期改变 profile 映射：「requires a process restart」）。
  走插件面板装则可免重启（它自己会重算并发布解析）。

## 七、我的推荐

R2 的发现让我**把推荐从「方案 A」改成了「方案 B + C 组合」**。原因是两个硬事实：

1. 方案 A 会撞上「子槽不能重复声明」的死局，实际代价是 vendoring 约 4100 行 —— 那是 fork，不是插件；
2. 数据层过滤会把会话赶到「未分组」里，恰好不是你要的效果。

所以推荐：

> **方案 C（CSS 就地隐藏）+ 方案 B（面板作为管理界面），共用第四节的独立存储层。**

具体形态：

- 隐藏效果走 `div:has(> [data-row-key="workspace:<uuid>"])` —— 这是**唯一**能就地连组带会话一起藏、
  且不用 fork 的方式；
- 「显示已隐藏工作区 / 取消隐藏」的界面挂在 `sidebar.panellist` 面板里（干净、无 hack、一整套标准设施）；
- 状态存插件自己的 `workspaces_hidden` domain（跨端同步、可恢复、不碰上游 schema）；
- 隐藏模式下**禁用工作区拖拽**并**关掉行过渡**，规避 R2 指出的两个隐患。

这是一条「先能用、代价可控、随时可升级」的路线。如果哪天官方加上了工作区级菜单槽，
再平滑迁到正规插件形态即可——存储层不用动。

打包上建议**一开始就打成 bundle**（§6.3），这样你随时能在插件面板里开关、卸载它。

## 八、需要你决定的事

1. **接受「CSS 就地隐藏 + 面板管理」这个组合吗？**
   还是说你更希望「设计上绝对正确、愿意为此 fork 整个包」（方案 A，约 4100 行 + 长期跟随官方）？
2. **隐藏的粒度**：连组带会话一起藏（推荐），还是只藏组头？
3. **隐藏的工作区还要不要能被搜索到？能被 "New session" 选中吗？**
   （注意：搜索行不走 `data-row-key`，默认**仍然能搜到**；如果要一并屏蔽需要额外处理。）
4. **隐藏模式下是否禁用工作区拖拽？**（R2 指出对着隐藏兄弟拖拽会产生看不见的换序，我建议禁用。）
5. 要不要配套**快捷键**（比如 `Ctrl+H` 隐藏当前工作区）。
